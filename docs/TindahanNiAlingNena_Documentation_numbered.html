Chapter 1

1. Introduction

1.1 Overview

Tindahan ni Aling Nena (Recoded) is a single-player, mouse-driven simulation game written in C# with Windows Forms. The player takes the role of the cashier at Aling Nena's neighbourhood sari-sari store. Each round presents a customer with a short grocery order and a payment assembled from Philippine bills and coins. The player must return the correct change by drawing notes and coins from a shared cash drawer, then confirm the transaction.

Although the presentation is a game, the core of the program is a small arithmetic and inventory system. Money is modelled as discrete denomination objects rather than floating-point values; the cash drawer is an inventory that grows when customers pay and shrinks when change is handed over; and the round is validated by comparing the value of the selected change against the difference between the payment and the order total. The game therefore provides a compact but genuine domain for demonstrating object-oriented design.

A round has three possible shapes. An exact-paying customer hands over the precise total, so no change is needed. An overpaying customer hands over more than the total and expects the difference. An underpaying customer hands over too little; the player must press Ask for more before change can be given. A correct answer increases the score and immediately produces the next customer. An incorrect answer clears the selected change, resets the score to zero, and lets the player try the same customer again. There is no terminal state: the session continues indefinitely, with orders growing as the score rises.

In one sentence

The program is an endless cashier drill that tests whether the player can compose an exact set of Philippine denominations from a limited shared drawer — built as a layered, event-driven WinForms application around a small object-oriented domain model.

1.2 Purpose and Audience

This document serves three audiences. For instructors and evaluators, it explains where and how the four pillars of object-oriented programming appear in the code, with file references and excerpts rather than generic definitions. For maintainers, it records the intended architecture, the rules encoded in the services, and the known weak points that should be addressed before extending the program. For readers new to the repository, it offers a guided path from the entry point to the individual classes, so that the code can be understood without reverse-engineering it from the debugger.

The document deliberately separates description from evaluation. Chapters 1–4 and 7–9 describe what exists. Chapters 5–6 and 10–11 assess how well it is designed and what should change. This distinction matters because several design choices are reasonable for a student project but would not survive a production review.

1.3 Scope and Method

The analysis covers the complete solution in the repository: the WinForms project, its 23 C# source files, the project file, the solution file, and the runtime assets required to play. Compiler-generated files under bin/ and obj/ were excluded, as were the contents of the .NET runtime and WinForms libraries.

Findings were produced by reading every source file, tracing the event wiring from Program.cs through GameSession and GameScreen, reconstructing the rules from the service methods, and performing a clean local build. The build completed with zero warnings and zero errors, which means the design observations in this document are not compiler diagnostics; they are architectural judgements. No automated tests exist in the repository, so runtime behavior was verified by code inspection rather than by executing a test suite.

1.4 Key Features

  • Procedural orders. Every customer receives one to four products (more as the score grows) drawn from a six-item catalog with Filipino store staples such as pandesal, instant noodles, and sardines.
  • Three payment behaviours. Customer subclasses generate exact, over-, or underpayments, producing three distinct cashier situations from one base contract.
  • Denomination-accurate money. Six bill values (₱20 to ₱1,000) and three coin values (₱1, ₱5, ₱10) are modelled as immutable-in-practice objects with images and sounds.
  • Shared cash drawer. A single drawer holds every piece in play, starts with ₱880, receives customer payments, and is decremented when change is handed over. Counts are displayed live on each denomination.
  • Exact-change validation. The selected change is summed and compared with the overpayment; an error clears the selection and resets the score.
  • Escalating difficulty. Order size increases with the score, gradually raising the arithmetic load and the number of items on the receipt.
  • Event-driven UI. The form raises intention events; the session raises state events. Neither side calls the other's methods directly at runtime.
  • Presentation assets. Customer portraits, bill and coin images, a receipt background, and five WAV sound effects are copied to the output directory by the project file.
  • Zero external packages. The program depends only on the .NET base class library and WinForms.

2. System Architecture

2.1 Architectural Style

The application uses a layered architecture with a passive view, a variant of the Model–View–Presenter pattern. Four concerns are separated by folders and namespaces: the domain models, the services that implement rules and generators, the UI controls, and a tiny composition root in Program.cs. A single GameSession object holds the mutable game state and acts as the presenter between the rules and the screen.

What makes the design distinctive is that the view is passive and the communication is event-driven in both directions. The form never reaches into the session to ask for data. Instead, it raises intention events — DenominationClicked, GiveChangeClicked, ClearClicked, AskForMoreClicked — and the composition root subscribes the session's methods to them. In the opposite direction, the session raises StateChanged, MessageSent, and CustomerStarted; the composition root subscribes the form's display methods. The two halves therefore know nothing about each other's types, only about delegate signatures.

2.3 Layer Responsibilities

Presentation. GameScreen is the window shell. It creates and arranges the four display controls, exposes intention events, and offers three display methods: ShowState, ShowMessage, and ShowCustomer. It contains no scoring, no payment rules, and no drawer bookkeeping. Each child control is equally focused: CustomerDisplay paints a portrait, OrderDisplay formats receipt text, DenominationPanel builds the drawer grid and raises a click event, and DenominationButton wraps one denomination image.

Application. GameSession is the only stateful service. It answers four questions: what is being sold, who is paying, what has the customer paid, and what change has the player selected. It also owns the score and orchestrates the transition from one customer to the next. The class exposes seven operations in total — four commands (Start, AddChangePiece, ClearChange, GiveChange, AskForMore) and three events.

Domain services. These are deliberately small. ProductCatalog owns the six products. OrderGenerator turns a size range into an Order. PaymentGenerator turns an amount into a list of denominations. ChangeChecker answers arithmetic questions. CashDrawer is an inventory of physical pieces. NameGenerator composes a title and a first name by gender. AudioPlayer is infrastructure rather than domain logic, but it lives in the same folder for convenience.

Domain model. The entities own the behaviour that naturally belongs to them: an Order knows its products and total, a Product knows its name and price, a Customer knows how to produce a payment, and a Denomination knows its value, image, and sound.

2.4 Dependency Rules

The intended dependency direction is downward: UI depends on services and models, services depend on models, and the composition root depends on everything. That rule holds for the majority of the code. GameSession imports only Models and Models.Money; it never mentions a WinForms type. This is what allows the session to be exercised without opening a window, at least in principle.

Two upward edges break the pure layering. Customer.GeneratePayment takes a PaymentGenerator, a service type, so Models.Customers depends on Services. Bill.PlaySound and Coin.PlaySound call AudioPlayer, so Models.Money also depends on Services. At the namespace level the dependency is therefore bidirectional. In practice this is harmless in a project of this size, but it means the model cannot be compiled or reused without the service assembly, and it makes the sound effect a hard-wired side effect of a domain object. Chapter 6.7 proposes moving playback behind an interface to restore a single direction.

A second observation is that all dependencies are on concrete classes. There are no interfaces in the repository, and GameSession constructs its own collaborators (new ProductCatalog(), new CashDrawer(), and so on). This simplifies reading but prevents substituting fakes in tests and makes the session responsible for assembling its own dependencies.

2.5 Event-Driven Communication

Events are the contract between the two halves of the program. The form publishes what the player did; the session publishes what changed. The composition root connects matching signatures, so both classes remain unaware of each other.

The trade-off is that failures inside a handler propagate straight back into the publisher, and there is no automatic unsubscription. Because the session and the form live for the entire process, the absence of -= calls is not a leak in practice, but it would become one if screens were created and destroyed repeatedly.

The state event carries six values rather than an object. It works, but the signature is fragile: adding a seventh value changes every subscriber, and the ordering of two int parameters (amount paid and change given) is easy to confuse. A small immutable GameState record would make the contract self-documenting. This is discussed again in Chapter 6.

3. Domain Model

3.1 Domain Overview

The domain contains five concepts that matter to the player: a product, an order, a customer, a denomination, and the cash drawer. Products and orders describe what is being sold. Customers describe who is paying and how much. Denominations describe the physical money. The drawer is the shared inventory from which change is assembled. Everything else — catalogs, generators, checkers, names, audio — exists to create or manipulate those five concepts.

Two consequences follow from the static registry. First, it is a multiton (a controlled set of named instances): identity can be compared by reference for the nine values, although the program never relies on that. Second, every payment list and every change list contains references to the same objects. That is efficient and conceptually correct for money, whose value is intrinsic, but it also means the objects must be treated as immutable. In this code they are not strictly immutable: Value and ImagePath have public setters. A caller could change ₱20 into ₱500 for every holder at once. Nothing in the program does so, but the design would be safer with { get; private set; } or constructor-only initialization.

The integer type is the right choice. All prices and payments are whole pesos, and using int avoids the rounding errors that would appear if money were stored as float or double (for example, repeated subtraction in the payment builder). The limitation is that the model cannot represent centavos; that is acceptable for this game, whose smallest unit is the ₱1 coin.

3.4 Customer Model

Customer is abstract. Its constructor accepts the order, flips a coin to choose a gender, and asks NameGenerator for a matching name. It exposes read-only accessors for the name, gender, and order, and declares a single abstract method:

Models/Customers/Customer.cspublic abstract class Customer
{
    protected Order order;
    private Gender gender;
    private string name;

    public Customer(Order order)
    {
        this.order = order;
        gender = random.Next(2) == 0 ? Gender.Male : Gender.Female;
        name = NameGenerator.GenerateName(gender);
    }

    public abstract List<Denomination> GeneratePayment(PaymentGenerator paymentGenerator);
}

Each subclass overrides only that method, delegating to a different method on the same generator. The result is a very small but genuine application of inheritance and polymorphism: the session can ask any customer for a payment without knowing which payment strategy is in play.

Names are assembled from a title and a first name: Pareng/Kuya/Mang/Tatay/Tito for men and Mareng/Ate/Aleng/Nanay/Tita for women, paired with ten common Filipino first names each. The generator picks uniformly, so there are 50 male and 50 female combinations. The same pool is reused for every customer, which is why names repeat during a long session.

The Gender enum is declared in the global namespace rather than inside Models.Customers. It is therefore visible everywhere without a using directive, including in the UI layer. This works, but it leaks a domain detail into the global scope and is inconsistent with every other type in the project.

4. Game Mechanics

4.1 Game Loop

The program has no explicit state-machine class; the loop is encoded in the methods of GameSession. The implicit states are:

  1. Ready. A customer exists, the payment has been placed in the drawer, and the selected change list is empty.
  2. Selecting change. The player adds pieces one by one. Each addition is checked against the drawer and re-renders the state. The state persists until the player confirms or clears.
  3. Validation. GiveChange compares the selected sum with the required change and either accepts or rejects the attempt.
  4. Transition. On success, the score increases and a new customer is built immediately. On failure, the selection is cleared and the score resets to zero; the same customer remains.

Underpayment adds a sub-state: while paid < total, giving change is refused and the only productive action is Ask for more, which appends money until the payment covers the order. There is no timer, no move limit, and no game-over state.

4.3 Order Generation

On every new customer, StartNextCustomer calls orderGenerator.GenerateOrder(1, 4 + score). OrderGenerator chooses a count uniformly in that inclusive range and repeatedly asks the catalog for a random product. With a score of zero, the order contains one to four items. At a score of ten it contains one to fourteen. Because the catalog is uniform, the expected price of one line is ₱10.17 (the mean of 1, 2, 6, 12, 15, and 25), so the expected initial order is about ₱25.42 for 2.5 items.

4.5 Payment Generation

PaymentGenerator flattens the bill and coin registries into one list sorted from smallest to largest. Its central routine, BuildPayment, repeatedly collects the denominations that still fit the remaining amount, picks one uniformly at random, appends it, and subtracts its value. The loop always terminates because the ₱1 coin fits every positive remainder.

Services/PaymentGenerator.cs — core algorithmprivate List<Denomination> BuildPayment(int targetAmount)
{
    var paymentDenominations = new List<Denomination>();
    int amountLeftToCover = targetAmount;

    while (amountLeftToCover > 0)
    {
        var denominationsThatStillFit = new List<Denomination>();

        foreach (var denomination in _allDenominations)
        {
            if (denomination.Value <= amountLeftToCover)
                denominationsThatStillFit.Add(denomination);
        }

        int randomIndex = _random.Next(denominationsThatStillFit.Count);
        var chosenPiece = denominationsThatStillFit[randomIndex];

        paymentDenominations.Add(chosenPiece);
        amountLeftToCover -= chosenPiece.Value;
    }

    return paymentDenominations;
}

The three public methods wrap this routine with different targets:

MethodTarget logicGuarantee
GenerateExactPayment(amount)Build exactly amount.Sum = amount.
GenerateUnderPayment(amount)Pick a random target in [1, amount-1]; for amount = 1, return an empty list.Sum < amount.
GenerateOverPayment(amount)Choose maxOver = max(10, amount / 2); pick a random extra in [1, maxOver]; target = amount + extra.Sum > amount.

All three reject non-positive inputs with ArgumentOutOfRangeException. The random choice among fitting denominations biases the output toward smaller pieces: for a ₱25 target, the fitting set contains 1, 5, 10, and 20, so a ₱20 note is chosen only one time in four; once the remainder falls below 20, only smaller pieces remain. Consequently, generated payments contain many coins, and large bills appear mainly when the target itself is large. This is plausible cashier behaviour, but it is not modelled on how real customers choose notes.

Subtle behaviour

AskForMore calls GenerateOverPayment(orderTotal - amountPaid). The argument is the shortfall, not the total, so the generated extra is relative to the shortfall. For example, if the order is ₱100 and the customer paid ₱80, the generator targets ₱20 plus up to ₱10 extra, producing a payment between ₱101 and ₱110 in total. The customer therefore ends up overpaying, and change is required. This is likely intentional — it creates a change-giving step — but the method name alone does not communicate it.

4.6 Change Validation and Scoring

ChangeChecker is deliberately arithmetic-only. GetTotal sums a list, CountPieces counts occurrences of a value, and IsChangeCorrect returns GetTotal(changeGiven) == amountPaid - orderTotal. There is no notion of an "optimal" or "expected" set of denominations: any combination that sums to the overpayment is accepted, even if it empties the drawer of coins unnecessarily.

4.7 Difficulty and Balance

The economy is conservative in total value but fragile in denomination mix. On every successful round the drawer gains the customer's payment and loses the player's change. Since payment - change = order total, the drawer's total value rises by the order total each round. Nothing removes money from the system. After a long session the drawer can be worth many thousands of pesos.

However, total value is not the same as usable change. The drawer can accumulate large bills while running short of ₱1, ₱5, and ₱10 coins, because BuildPayment favours small pieces and players may spend coins to satisfy exact sums. If the coins run out, the player may be unable to form the required amount even though the drawer is rich in notes, and there is no exchange or "break a bill" action. The game does not detect this dead end. In practice it is rare early on, because the starting drawer contains 60 small coins and every customer payment replenishes the pool, but it becomes possible in long sessions. A future version should either add a bill-breaking action or track a "can make change" invariant and restock when it is violated.

Other balance observations:

  • No time pressure. The player can calculate indefinitely; the challenge is arithmetic accuracy, not speed.
  • No loss condition. The session always continues, which makes the game a drill rather than a survival challenge.
  • Reset-only penalty. Wrong change is punished by losing the streak but not by losing money or customers.
  • Fixed customer mix. The 10/70/20 split never changes, so later rounds are not more varied, only larger.
  • Order size cap. There is no cap; at very high scores the receipt can contain dozens of lines and the order value can exceed ₱1,000, which the payment generator can still represent because the ₱1,000 bill is registered.

5. The Four Pillars of OOP

5.1 Overview

Object-oriented programming rests on four ideas: encapsulation (protect state behind a controlled interface), abstraction (model the essential and hide the incidental), inheritance (derive specialised types from a general one), and polymorphism (let one call site produce different behaviour depending on the runtime type). The program applies all four, but not to the same degree. Encapsulation and inheritance are pervasive; abstraction is concentrated in two abstract base classes; polymorphism is genuine but limited to the two domain hierarchies, the event delegates, and the WinForms overrides.

The table below is the short version. The rest of the chapter supports each claim with code evidence and then notes where the implementation falls short of the ideal.

Abstractionabstract Customer, abstract Denomination, the GameSession command surfaceClear and purposeful, but the abstract contracts say little about what implementations must guarantee.
InheritanceThree customer subclasses; Bill/Coin; five UI types deriving from WinForms controlsShallow (depth two), well motivated, and closed with sealed where appropriate.

Supporting language mechanics

The pillars are supported by ordinary C# features that are worth naming in a design review: classes and objects, constructors (including base(order) chaining), fields versus properties, access modifiers, static members, readonly fields, constants, enums, delegates and events, generics (List<T>, Dictionary<TKey,TValue>), nullable reference types, pattern matching, and IDisposable. The project uses all of these; it does not use interfaces, records, generics of its own, operator overloading, indexers, or user-defined exceptions.

5.2 Encapsulation

Encapsulation is the bundling of state with the operations that maintain it, plus the restriction of direct access from outside. The clearest examples are the small data-holding classes. Where encapsulation leaks

  • Order.GetProducts() returns the internal List<Product>. A caller can Add or Remove items without updating totalCost, breaking the class invariant. Returning IReadOnlyList<Product> or a copy would close the leak.
  • Customer.GetOrder() returns the mutable Order. This is currently harmless because only the session reads it, but the door is open.
  • Denomination.Value and ImagePath have public setters. Since all nine objects are shared, mutating one would change it everywhere. Prefer { get; private set; } or constructor-only fields.
  • Bill.Denominations exposes a mutable Dictionary. External code could add, remove, or replace entries. A read-only wrapper would preserve the closed set.
  • Customer.order is protected rather than private, so subclasses could reassign the field. They currently only read it.

These are not functional bugs today, because the program is small and disciplined about access. They are, however, exactly the kind of boundary weakness an evaluator should be able to identify: encapsulation is not just "fields are private", it is "no path exists to an inconsistent state".

5.3 Abstraction

Abstraction means describing what a thing does and hiding how it does it. The project has two textbook examples, both abstract classes:

The base class defines a contract and supplies the shared parts (order, gender, name). The subclass supplies only the variable part. A caller that holds a Customer reference does not need to know whether the payment will be exact, over, or under; it only needs to know that a list of denominations will come back. That is the essence of abstraction: a stable interface over varying implementations.

GameSession is a second kind of abstraction, even though it is a concrete class. Its public surface — Start, AddChangePiece, ClearChange, GiveChange, AskForMore, and three events — hides the entire machinery of orders, payments, drawer bookkeeping, and scoring. The UI does not know that a ChangeChecker exists, nor that the drawer is a list of denomination references. It knows only the commands and the state notification.

The UI layer also relies on abstraction through the WinForms base classes. CustomerDisplay does not reimplement mouse handling, layout, or painting infrastructure; it inherits it and overrides only the two hooks it needs. OrderDisplay inherits scrolling and background painting from Panel. This is framework-level abstraction: the base class defines the template, the subclass fills in the specific behaviour.

Weaknesses of the abstractions

  • Customer.GeneratePayment has no documented postcondition. The base class does not say that the returned sum must equal, exceed, or fall short of the total; those relationships exist only in the three implementations and in comments in PaymentGenerator. A stronger contract would be visible to callers and testable.
  • Customer hard-codes random gender selection in its constructor, so a caller cannot create a customer with a known gender for testing. The abstraction hides too much: identity generation is not a customer responsibility.
  • Denomination.PlaySound hard-wires audio playback into the domain object. A cleaner abstraction would let the domain describe the kind of sound and let infrastructure play it.
  • There are no interfaces. A ChangeChecker could be an IChangeChecker, a CashDrawer an IDrawer, and AudioPlayer an ISoundPlayer, allowing substitutes in tests. The absence is acceptable for a 1,456-line program but limits testability and extension.

The program also uses composition where inheritance would be wrong. GameSession does not inherit from CashDrawer; it has a drawer. Customer does not inherit from Order; it has an order. The main limitation is that customer variation is modelled as a class hierarchy when it could be a strategy object. Adding a "customer who pays with a rounded-up amount" requires a new class and a change to the factory logic in GameSession. A single Customer class holding an IPaymentStrategy would allow new behaviours without touching the factory. For three behaviours this is a matter of taste; the current design is more readable for a beginner audience.

A delegate is a type-safe reference to a method. The event wiring in Program.cs is polymorphism of behaviour: the same event invocation can call different methods depending on what was subscribed.

The same mechanism allows multiple subscribers; the program happens to use one per event. The lambda for CustomerStarted is a small adapter that fixes one argument (CustomerState.Normal) and forwards the gender.

4. Framework overrides

WinForms calls virtual methods on the base control at well-defined times. CustomerDisplay overrides OnPaint to draw the portrait with cover scaling, and Dispose(bool) to release the cached image. The framework holds a PictureBox reference but executes the derived implementation. This is the template-method pattern in practice: the base class defines the algorithm, the subclass fills in a step.

Where polymorphism is replaced by conditionals

Two places bypass runtime dispatch and inspect type or category instead:

  • DenominationButton asks if (denomination is Bill) to decide whether to rotate the image. A virtual property such as bool IsPortrait or a DisplayRotation on Denomination would let the object decide, removing the type test. This is the classic "switch on type" smell.
  • CustomerDisplay.GetRandomCustomerNumber uses a switch expression on Gender?, and NameGenerator.GenerateName uses an if/else on Gender. These are simple two-way data selections, so a conditional is defensible; a lookup table or a small gender-profile object would be more extensible.

There is no method overloading or operator overloading in the project, so compile-time polymorphism is not part of the design. All interesting dispatch is runtime dispatch through virtual methods or delegates.

Liskov substitution

The three customer subclasses are substitutable in the narrow sense that all return a valid List<Denomination>. They are not substitutable under an implicit "payment covers the total" contract, because UnderpayingCustomer deliberately violates it. The program works because the caller handles the underpaid case explicitly. This is a good discussion point: the base contract is intentionally weak, and the subtype's behaviour is a different situation, not a violation of a stated rule.

5.6 How the Pillars Cooperate

The pillars are easiest to see when tracing a single interaction. Consider the player double-clicking a ₱20 bill:

  2. Abstraction: the button holds a Denomination, not a Bill. The session accepts a Denomination. Neither side depends on the concrete money type.
  3. Polymorphism: piece.PlaySound() dispatches to Bill.PlaySound and plays paper.wav; the same line would play coin.wav for a coin.
  4. Encapsulation again: CashDrawer.GetPieceCount checks supply without revealing the internal list. GameSession updates its private changeGiven list and raises StateChanged; the view cannot mutate that list.
  5. Inheritance: when a new customer arrives, the session constructs one of three subclasses. The shared name, gender, and order initialisation runs in the base constructor, so the subclasses contain only the payment line.
  6. Polymorphism again: the next call to GeneratePayment runs the subclass version. The session does not branch on customer type after construction.

6.4 Observer Pattern

The relationship between GameSession and GameScreen is an implementation of the Observer pattern using C# events. The session is the subject: it exposes three events and invokes them when its state changes. The form is the observer: it subscribes methods that update the display. Program.cs plays the role of the assembler that registers the observer with the subject.

Compared with the classic pattern, the C# version removes the need for an IObserver interface and an Attach/Detach list. A delegate field is the observer list, and +=/-= are the registration methods. The trade-off is that the contract is a method signature rather than a named interface, so the compiler cannot tell you which methods are valid observers beyond matching parameter types.

Benefits. The session has no reference to the UI, so the rules can be tested or reused with another view. The form has no reference to the session, so controls can be rearranged without touching game logic. New observers (a log window, a sound controller) could be added in Program without changing either class.

Costs. Control flow is not visible at the call site: a method that calls SendState() indirectly runs UI code. Exceptions in a subscriber propagate back into the publisher. There is no unsubscribe, so a short-lived view would leak. And the six-argument StateChanged signature is easy to misuse; a dedicated GameState type would make the notification self-describing.

Other resources are less strict. DenominationButton loads an image and never disposes it; there are only nine buttons, so the leak is bounded and lasts for the process lifetime. OrderDisplay loads a receipt background and does not dispose it. Each DenominationButton creates a ToolTip, which is a component and should be disposed but is not. AudioPlayer caches SoundPlayer instances without disposing them; again, the cache is process-wide and small. These are acceptable for a desktop toy but would be flagged in a long-running application.

One positive detail is that AudioPlayer calls player.Load() when caching, so the first play does not pay the disk-read cost. SoundPlayer.Play() is asynchronous and returns immediately, which keeps the UI responsive.

6.6 Coupling and Cohesion

Cohesion is high in the small types: Product only holds product data, ChangeChecker only does arithmetic, and NameGenerator only composes names. GameSession has lower cohesion because it is the orchestrator, but its methods all serve the same round. GameScreen has the lowest cohesion: it builds five control trees, computes an absolute layout, re-raises four events, and formats three kinds of display. At 272 lines it is still readable, but it is the class most likely to grow into a maintenance problem.

7.1 Screen Composition

The main window has a fixed logical size of 1280×850 pixels and a minimum of 1000×700. It uses an overlay layout rather than docked panels: the customer portrait occupies the left 54% of the client area and runs the full height; the header, receipt, and action buttons occupy the right side; the cash drawer spans the full width across the bottom and sits on top of the portrait area. The arrangement is intended to resemble a counter: customer on the left, receipt and till controls on the right, drawer in front of the cashier.

7.4 Event Wiring

Eight subscriptions in Program.cs connect the two halves. The chain for a denomination click illustrates the path:

  1. DenominationButton.DoubleClick fires inside a slot.
  2. DenominationPanel.OnDenominationButtonClicked casts the sender and raises DenominationClicked(denomination).
  3. GameScreen.OnPanelDenominationClicked re-raises its own DenominationClicked.
  4. GameSession.AddChangePiece receives the piece because Program subscribed it.
  5. The session updates its state and raises StateChanged.
  6. GameScreen.ShowState updates the receipt, button caption, score, and drawer counts.

The action buttons follow a shorter path: the click handler first plays button.wav (an extra subscription added inside AddActionButton), then invokes the UI event. This guarantees consistent click feedback even when the resulting action is a failure. The Give Change button's caption is also the live change total, so the player can see the sum before committing.

7.6 Accessibility

The program makes a genuine start on accessibility. Each denomination button sets AccessibleName ("₱20") and AccessibleDescription ("Add a 20 peso denomination to the change"), and each count label updates its AccessibleName to a phrase such as "3 pieces of 20 pesos". Tooltips repeat the value. The receipt uses a real Label, so its text is available to screen readers, and the score is a label rather than a painted graphic.

The gaps are more significant than the wins. PictureBox is not a focusable button, so a keyboard-only user cannot tab to a denomination or activate it; there is no KeyDown handler, no access key, and no focus rectangle. Double-click activation is a motor-accessibility barrier. The fixed font sizes do not scale with system text settings, and the layout assumes a minimum width of 1000 pixels. The drawer counts are visually tiny. A future pass should add keyboard focus and Enter/Space activation, support single-click as an option, announce score changes through an accessible live region, and offer a high-contrast theme.

8. User Guide

Objective

Serve each customer correctly and keep the streak alive. A customer orders one or more items; the receipt shows every product, the total, and the amount the customer has handed over. Your job is to take notes and coins from the cash drawer until the selected change exactly equals the overpayment, then press Give Change. A correct answer increases the score and brings the next customer. A wrong answer clears your selection and resets the score to zero.

Controls

ActionHowEffect
Add a note or coinDouble-click its picture in the cash drawer.Appends one piece to the selected change and plays a paper or coin sound. The count on the slot is the number still available.
Give changeClick the green Give Change: P<sum> button.Validates the selected sum and either advances to the next customer or reports an error.
Clear selectionClick Clear.Returns every selected piece to the drawer conceptually; the list is emptied without penalty.
Ask for more moneyClick the gold Ask for more button.Only useful when the customer has paid less than the total. Adds another generated payment and puts it in the drawer.

Playing a round

  1. Read the customer's name and order on the receipt. Confirm the total.
  2. Read the line Customer paid. If it is lower than the total, press Ask for more first.
  3. Subtract the total from the amount paid. That difference is the change you owe.
  4. Double-click notes and coins whose values add up to that difference. Watch the Give Change caption; it shows the running sum.
  5. If you overshoot or change your mind, press Clear and start again. Clearing is free.
  6. Press Give Change. Success increments the score; failure resets it to zero but keeps the same customer.
Worked example

Order: Pandesal ₱2 + Instant Noodles ₱12 + Candy ₱1 = ₱15. The customer pays ₱50. Change due = ₱35. Suitable combinations include ₱20 + ₱10 + ₱5, or ₱10 + ₱10 + ₱10 + ₱5, or ₱20 + ₱5 + ₱5 + ₱5. Any combination summing to ₱35 is accepted, provided the drawer holds the pieces. The button reads Give Change: P35 before you confirm.

Scoring and strategy

  • Score +1 for every correct change. A wrong answer resets the score to zero; there is no partial credit.
  • Order size grows with the score. At score 0 the customer buys 1–4 items; at score 10, 1–14. Expect longer receipts and larger totals as you progress.
  • Conserve small coins. The drawer can run short of ₱1, ₱5, and ₱10 coins if you always spend them. Prefer larger pieces when the arithmetic allows, so you keep the flexibility to make odd amounts later.
  • Use Clear liberally. Rebuilding a selection costs nothing; a wrong confirmation costs the streak.
  • Check underpayments first. If the paid amount is below the total, no change combination can succeed until you ask for more.
  • There is no timer. Take the time to add carefully; the game rewards accuracy, not speed.

Common mistakes

SymptomCauseFix
"The customer didn't pay enough! Ask for more money."You pressed Give Change while the payment was below the total.Press Ask for more, then recalculate the change.
"The customer already paid enough!"You pressed Ask for more when the payment already covered the total.Give the change instead.
"No more P20 left in the drawer!"You selected more pieces of that value than the drawer holds, counting what you have already selected.Clear some selections or use a different combination.
"Wrong change! Try again."The selected sum did not equal paid minus total.Clear, recalculate, and rebuild the change. The score has already reset.

Abstraction. A simplified model that exposes what is essential and hides implementation detail. In this project, Customer and Denomination.

Aggregation. A whole–part relationship in which the parts can exist independently. CashDrawer aggregates shared denomination objects.

Association. A structural link between objects. Customer is associated with one Order.

Cohesion. How strongly the responsibilities inside one class belong together. High cohesion is desirable.

Composition. A whole–part relationship in which the whole owns its parts. Order composes its product list; GameSession composes its services.

Constructor. The special member that initialises a new object. Bill and Coin use private constructors to control creation.

Coupling. The degree to which one type depends on another. Low coupling between UI and session is achieved with events.

Delegate. A type-safe reference to a method. Action<T> is used for every event in the project.

Dependency inversion. Depending on abstractions rather than concrete implementations. Not applied in this project.

Encapsulation. Bundling state with the methods that maintain it and restricting direct access. See private fields and controlled events.

Event. A member that lets a publisher notify subscribers. StateChanged is the central example.

Flyweight / multiton. Sharing a small set of instances instead of creating many. The nine denomination objects behave this way.

Inheritance. Deriving a subtype from a base type. OverpayingCustomer inherits from Customer.

Instance. A concrete object created from a class. The drawer holds many references but only nine distinct denomination instances.

Interface. A contract without implementation. The project defines none, which limits substitution and testing.

Liskov substitution. Subtypes should be usable wherever the base type is expected without breaking the caller's assumptions.

Multiton. A pattern that restricts a class to a fixed, named set of instances, one per key. See Bill.Denominations.

Nullable reference types. A C# feature, enabled here, that distinguishes nullable from non-nullable references at compile time.

Object. A runtime instance of a class, with state and behaviour.

Observer. A pattern in which a subject notifies registered observers of changes. Implemented with C# events.

Override. Replacing a virtual or abstract base implementation. GeneratePayment is overridden three times.

Polymorphism. One call site, many runtime behaviours. piece.PlaySound() is the clearest example.

Property. A member that exposes a field through get/set accessors. Value and ImagePath are properties.

Sealed. A modifier that prevents further inheritance. Applied to Bill and Coin.

SOLID. Five design principles: single responsibility, open/closed, Liskov substitution, interface segregation, dependency inversion.

Static. A member that belongs to the type rather than an instance. Registries, generators, and the audio cache are static.

UML. Unified Modeling Language, used here for the class diagram and relationship vocabulary.

Virtual dispatch. The runtime selection of an overridden method based on the object's actual type.
